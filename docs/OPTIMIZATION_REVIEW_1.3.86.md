# astrbot_plugin_selfie_image 当前优化方案

> 评估基线：插件 `1.3.86`，分支 `main`，2026-08-19 代码巡检。  
> 目的：在不破坏现有自拍、合影、晒腿、批量生图和视频能力的前提下，明确下一阶段可落地的优化顺序。

## 一、当前状态与巡检结论

当前插件已经具备以下能力：

- 图片任务按“所有请求合计的图片张数”共享并发槽位，默认上限为 10。
- 生图任务支持后台执行、任务号、任务查询和取消入口。
- 生图渠道支持模型链路回退、超时预算、多 API Key 轮换和错误分类。
- 已有配置预检、缓存回收保护、参考图收集、协议锁定、Dashboard 和 Web 面板。
- 已有 `unittest` 核心回归测试；本次巡检前基线为 214 个测试通过。
- 生成记录、使用统计、图片缓存和视频缓存均落在插件数据目录，不写入仓库。

本次重点发现：

1. 图片调度和后台任务已经有基础，但任务状态主要保存在进程内；插件重载或进程重启后，正在执行任务的可查询性和恢复能力有限。
2. `generator.py` 已经记录每个渠道/Key 的尝试、耗时和错误分类，但缺少面向运营的成功率、排队时间、失败类别和 P50/P95 耗时汇总。
3. 生图失败已经能输出脱敏错误，但单张和批量文案需要继续统一；失败结果、部分成功和“请求成功但未返回有效图片”应形成明确状态模型。
4. 图片请求对“可重试”和“可能已扣费”已经有谨慎处理，但重试策略还应进一步区分网络失败、限流、服务端错误、参数错误、审核拒绝和创建超时。
5. “构图跑偏”不能只靠继续堆提示词解决。当前更需要先保留最终 prompt、比例、参考图数量、模型和渠道等非敏感元数据，再用真实样本判断是提示词、参考图、比例、裁切还是模型差异造成的。
6. 现有 `main.py` 仍然较大，命令入口、任务调度、记录持久化、错误文案和部分 Web 逻辑耦合较多；短期不宜大规模重构，应采用小模块、纯函数和测试先行的方式逐步拆分。

## 二、优化优先级总表

| 优先级 | 方案 | 主要收益 | 风险 | 建议批次 |
|---|---|---|---|---|
| P0 | 统一任务状态和结果统计 | 修复“成功/失败/部分成功”语义混乱，提升可查询性 | 可能影响旧任务记录兼容 | 第一批 |
| P0 | 错误分类与安全重试策略 | 减少无意义重试和重复扣费，提升可恢复失败成功率 | 规则错误可能导致重复请求 | 第一批 |
| P0 | 单图/批量进度与失败文案统一 | 直接改善当前用户体验 | 旧测试和文案断言需同步 | 第一批 |
| P1 | 生成观测与诊断面板 | 能定位哪个渠道、模型或 Key 在失败 | 统计数据会增加存储和隐私管理成本 | 第二批 |
| P1 | 构图策略模板与真实样本评估 | 降低构图跑偏，提升自拍一致性 | 过度约束会降低创作自由度 | 第二批 |
| P1 | 任务队列持久化、恢复和取消 | 重启后不丢任务状态，长任务更可靠 | 需要处理进程退出和重复执行 | 第三批 |
| P1 | 图片缓存生命周期和发送可靠性 | 降低磁盘膨胀、孤儿文件和发送失败 | 清理规则错误可能误删用户仍需图片 | 第三批 |
| P2 | 多 Key/多渠道健康度与熔断 | 避免持续打坏渠道，降低延迟 | 熔断状态管理较复杂 | 第四批 |
| P2 | 幂等与重复请求去重 | 避免用户重复发送造成重复扣费 | 相似请求判定可能误合并 | 第四批 |
| P2 | 配置迁移、导入导出和升级提示 | 降低版本升级后的配置问题 | 旧格式兼容分支增多 | 第四批 |
| P2 | `main.py` 渐进式拆分 | 降低维护成本和回归风险 | 拆分期间容易引入导入/生命周期问题 | 持续进行 |

## 三、详细实施方案

### P0-1：统一任务状态和结果统计

#### 目标

把一次生图任务的状态统一为：

- `queued`：已受理，等待并发槽位。
- `running`：至少一张图片正在生成。
- `succeeded`：全部请求成功并产生有效文件。
- `partial_success`：部分图片成功，部分失败。
- `failed`：没有产生有效图片。
- `cancelled`：用户主动取消或插件终止。
- `expired`：任务记录超过保留时间。

每个任务至少保存：任务号、创建时间、开始时间、结束时间、请求总数、成功数、失败数、取消原因、使用模型、最终错误类别和文件相对路径。不得保存 API Key、完整 Authorization、参考图原始内容或完整敏感提示词。

#### 建议修改文件

- `main.py`：统一命令和 Web 任务的状态转换、部分成功返回值和任务终态。
- `models.py`：增加任务结果的结构化字段或兼容解析函数。
- `dashboard_api.py`、`web.py`：统一状态显示和筛选。
- `tests/test_core.py`：覆盖全成功、全失败、部分成功、取消、重启读取旧记录。

#### 实施步骤

1. 先写状态转换纯函数，不直接改网络请求。
2. 为单图和批量结果统一生成 `requested/succeeded/failed/skipped` 计数。
3. 将当前 `success + files` 的兼容判断集中到一个函数。
4. 保留旧 JSON 字段读取能力，写入新字段时不删除旧字段。
5. 让 `/生图任务` 和 Web 查询返回同一套状态字段。

#### 验收标准

- 单张失败只显示失败，不出现批量进度。
- 多张部分成功显示成功数/失败数，并且任务终态为 `partial_success`。
- 任务查询不依赖当前协程对象即可读取最近终态。

### P0-2：错误分类与安全重试策略

#### 目标

明确以下错误的处理方式：

| 类别 | 示例 | 默认动作 |
|---|---|---|
| `param` | 比例、尺寸、模型参数无效 | 不重试，提示修改配置 |
| `safety` | 内容审核拒绝 | 不重试，不泄露上游敏感原文 |
| `auth` | 401/403、Key 失效 | 换 Key 或换渠道，并标记渠道异常 |
| `rate_limit` | 429、额度不足 | 短退避后换 Key；不无限重试 |
| `network` | DNS、连接断开 | 同一请求最多有限次数重试 |
| `server` | 5xx、上游暂时繁忙 | 指数退避，仍失败再换渠道 |
| `timeout_create` | 创建请求超时，可能已扣费 | 不自动重复 POST，转为“待确认/未知” |
| `timeout_poll` | 异步任务轮询超时 | 继续查询或标记待确认，不重复创建 |
| `invalid_output` | 无图片、图片格式无效 | 换渠道；记录响应摘要 |

#### 建议修改文件

- `error_classify.py`：补充 `server`、`timeout_create`、`timeout_poll` 和 `invalid_output`。
- `generator.py`：使用统一的 retry budget、最大次数和退避时间。
- `providers.py`：返回 HTTP 状态、请求阶段和是否可能已创建的元数据。
- `tests/test_core.py`：用假响应覆盖每一类错误，禁止真实请求测试依赖密钥。

#### 关键约束

- 对可计费的创建 POST，不能因为客户端超时就盲目重发。
- 重试次数必须同时受“次数上限”和“全局超时”限制。
- 用户看到的错误必须脱敏，日志也不得记录密钥、完整 URL 查询参数或完整参考图数据。

### P0-3：统一进度、失败和取消文案

#### 目标

让单图、批量、排队、部分成功、取消和最终失败都使用同一套状态数据渲染文案，避免逻辑分支直接拼接互相矛盾的句子。

#### 建议修改文件

- `main.py`：抽出纯函数，例如 `render_generation_progress(state)`、`render_generation_failure(state)`。
- `prompt_templates.py`：如果继续使用 LLM 生成短失败文案，必须以确定性状态为准，LLM 只能润色，不能决定“是否继续”。
- `tests/test_core.py`：覆盖单张失败、多张第 1 张失败、多张最后一张失败、部分成功、取消和队列等待。

#### 规则

- `total == 1` 时不显示“第 1/1 张”“已出 0 张”“继续后面的”。
- 只有 `remaining > 0` 且任务确实会继续，才显示“继续”。
- 失败原因按类别输出可执行建议，例如“参数不支持，请改用 1K”或“上游限流，稍后重试”。
- 进度消息不能覆盖最终状态；最终消息必须明确成功数、失败数和任务号。

### P1-1：生成观测与诊断面板

#### 目标

回答以下运营问题：哪个模型失败最多、哪个 Key 经常 429、平均耗时多少、排队多久、失败集中在网络还是审核、缓存占用多少。

#### 建议指标

- 任务数、成功率、部分成功率、失败率、取消率。
- 各渠道/模型/Key 序号的成功率和失败类别计数。
- 排队耗时、单张生成耗时、端到端耗时的 P50/P95。
- 当前运行中图片数、排队任务数、最近一次渠道错误时间。
- 缓存文件数、缓存字节数、最近清理时间和清理数量。

#### 隐私要求

- 只保存渠道名、模型名、Key 序号，不保存 Key 本身。
- 提示词默认只保存长度、哈希或经过截断的非敏感摘要；参考图只保存数量和字节大小。
- Web 面板默认只展示聚合统计，不展示完整请求体。

### P1-2：构图策略模板与真实样本评估

#### 目标

针对“构图跑偏”建立可验证的改进流程，而不是盲目追加提示词。

#### 建议方案

1. 将构图拆成结构化字段：主体位置、镜头距离、视角、画面比例、动作、背景、裁切边界、参考图约束。
2. 为自拍提供至少三种策略：`自然自拍`、`半身稳定`、`全身构图`；默认使用保守策略。
3. 把硬约束放在 prompt 末尾，使用明确的边界语句，例如“保持主体位于画面中心区域”“不要裁掉头顶和脚部”等；不要把互相冲突的镜头要求同时注入。
4. 参考图处理区分“身份/服装参考”和“构图参考”，避免一张参考图同时承担所有约束。
5. 记录每次生成的比例、模型、参考图数量、策略名和 prompt 哈希，便于 A/B 对比。
6. 建立固定验收集：同一人物、同一动作、同一比例，每个策略生成固定数量，人工记录偏移类型。

#### 暂不建议

- 在没有实际失败图片和偏差描述前，直接修改全局默认 prompt。
- 用输出审核模型判断“构图好不好”；审核模型更适合安全性、清晰度和基本输出有效性检查。
- 将某个模型的构图修复词强行套到所有渠道。

#### 验收指标

- 头部/脚部被裁切率。
- 主体偏离中心的比例。
- 动作遵循率、参考图身份保持率。
- 各模型在三种策略下的失败率和耗时。

### P1-3：任务队列持久化、恢复和取消

#### 目标

插件重启后仍能查询历史任务，并对“已提交但未确认完成”的任务给出安全状态，不重复扣费。

#### 建议修改文件

- `main.py`：任务生命周期和恢复扫描。
- `utils.py` 或新增 `task_store.py`：原子写入任务 JSON、版本迁移和过期清理。
- `dashboard_api.py`、`web.py`：任务恢复状态展示。
- `tests/test_core.py`：模拟进程重启和半写入文件。

#### 关键设计

- 使用临时文件 + `os.replace` 原子写入。
- 每个任务记录 `created/running/terminal/unknown` 阶段。
- 创建请求超时但无法确认上游状态时标为 `unknown`，不自动再次 POST。
- 取消只能取消本地排队和未开始任务；已发往上游的请求显示“取消等待结果”，不能假装已撤回。
- 恢复任务默认只恢复查询和展示，不自动重放可计费请求。

### P1-4：图片缓存生命周期和发送可靠性

#### 目标

避免生成文件、视频文件、记录和消息发送状态之间不一致。

#### 建议步骤

1. 所有文件统一记录相对路径、大小、MIME、创建时间和发送状态。
2. 发送前验证路径必须位于 `image_cache` 或 `video` 目录内，且文件签名有效。
3. 发送失败不删除文件，记录为 `send_failed`，允许任务查询或手动重发。
4. 清理时优先删除已发送、未被任何记录引用且最旧的文件。
5. 清理过程中使用锁和临时索引，避免并发生成时误删刚写入文件。
6. 增加缓存清理的 dry-run 统计，先显示将删除什么，再执行删除。

### P2-1：渠道健康度、熔断和恢复

#### 目标

对连续失败的渠道短时间熔断，避免每次请求都浪费完整超时预算。

#### 建议规则

- 参数错误、审核拒绝不触发熔断。
- 连续网络/5xx/超时达到阈值后，渠道进入短暂 `cooldown`。
- 429 按 Retry-After 或指数退避处理。
- 成功请求恢复健康分数。
- 熔断状态只保存渠道名、模型名、失败类别、时间和计数，不保存 Key。

必须提供“立即恢复/清除健康状态”入口，防止错误判定长期屏蔽正常渠道。

### P2-2：幂等与重复请求去重

#### 目标

防止用户因网络无响应重复发送相同请求，造成重复扣费和重复图片。

#### 建议方案

对以下字段规范化后计算短期请求指纹：

- 用户/会话标识。
- 动作文本和结构化选项。
- 请求数量、比例、清晰度。
- 参考图哈希列表。
- 当前模型选择和配置版本。

短期窗口内相同指纹只提示已有任务号，不复制提交。必须允许用户明确使用“强制再生成”绕过去重，且不能把完整提示词或图片内容写入日志。

### P2-3：配置迁移、导入导出和升级提示

#### 目标

让旧版本从 `1.3.83`、`1.3.85` 升级到 `1.3.86+` 时，旧配置继续可用，并明确提示新增配置的默认值。

#### 建议步骤

- 为配置增加 `schema_version`，当前配置版本与插件版本分开。
- 每次迁移只做一次，并写入迁移结果日志。
- 对旧的并发配置保留用户显式值，不强行覆盖为新默认值 10。
- 导出配置时自动脱敏 API Key、Token 和代理认证信息。
- Dashboard 显示“当前配置来自旧版本/使用默认值”的提示。
- 增加配置导入前预览和失败回滚。

## 四、建议实施顺序

### 第一批：先修用户可见问题和结果语义

1. 完成当前单张失败文案修复的提交和回归。
2. 抽出统一结果统计，覆盖单图、批量、部分成功和取消。
3. 统一任务终态和 `/生图任务` 查询返回值。
4. 补齐错误阶段和错误类别，先实现“不重试创建超时”。
5. 增加 8 个核心回归场景：单图成功、单图失败、多图全成功、多图部分成功、多图最后一张失败、排队、取消、渠道超时。

### 第二批：再处理构图质量和可观测性

1. 加入构图策略字段和保守默认策略。
2. 记录非敏感生成元数据和 prompt 哈希。
3. 增加渠道/模型/错误类别统计。
4. 用固定样本进行 A/B 评估，再决定是否修改默认 prompt。

### 第三批：提升长期运行可靠性

1. 任务记录原子持久化和重启恢复展示。
2. 发送失败可重发。
3. 缓存 dry-run、清理统计和更严格的生命周期状态。
4. 渠道健康度和短暂熔断。

### 第四批：控制成本和维护复杂度

1. 请求指纹去重和强制重生成入口。
2. 配置 schema 迁移、脱敏导入导出。
3. 将纯函数和独立协议逻辑从 `main.py` 逐步移到小模块。
4. 每个拆分批次都必须先补测试，再移动代码，禁止一次性重写主文件。

## 五、统一验收基线

每个代码批次都必须执行：

```bash
python -m py_compile main.py models.py web.py providers.py generator.py error_classify.py
python -m unittest tests.test_core -q
git diff --check
```

涉及任务调度时还要验证：

- 并发上限为 10 时，`2 + 1` 可以同时运行。
- 已占满 10 个图片槽位时，第 11 张进入队列，释放槽位后继续。
- 单张失败不输出批量进度。
- 批量部分失败不重复占用或释放槽位。
- 取消排队任务不会发送图片，取消运行中任务不会伪造成功。

涉及真实渠道时：

- 使用专门测试配置，不把密钥、Token、代理认证或完整请求体写入日志。
- 先做单张 `n=1` 验证，再做小规模并发；禁止未经确认直接进行大批量计费请求。
- 创建请求超时不得自动重复 POST，避免重复扣费。
- 测试结果只记录成功数、失败类别、耗时和是否有有效图片，不保存凭据。

## 七、本轮已实施

以下内容已在当前工作区完成，尚未创建新版本发布提交：

- 单张失败不再显示批量进度和“继续后面的”。
- 批量结果统一补充 `requested_count`、`succeeded_count`、`failed_count` 和 `status`。
